# Frontend Functional Specification: Checkout, Orders, and Invoice (As-Built)

**Input**: CU-C05
**Status**: As-built / retrospective
**Scope**: Checkout form, payment-return presentation, buyer order history/detail, retry action, and invoice download. Order creation, payment verification, ownership, stock changes, and invoice issuance are BFF/Core/provider responsibilities described in the [canonical CU-C05 specification](../../../specs/005-checkout-orders-invoice-as-built/spec.md). The payment integration is sandbox-only.

Submission shows a pending state and sends `POST /api/v1/checkout` with the generated `CheckoutRequest` and Authorization header. | The BFF `checkout` operation returns `CheckoutResponse`; a successful response is passed to the payment-navigation helper. ## Boundaries and observed gaps

- Client-side checks cover required standard-delivery fields and presence of the local token. The BFF/Core remain authoritative for authentication, nonempty cart, shipping validation, order creation, totals, payment verification, retries, ownership, stock mutation, cart cleanup, and invoice generation.
- The result screen is driven by the browser return parameters, but a redirect alone is not treated as payment approval: the Frontend calls the BFF confirmation operation and renders the returned order state.
- The order-history status formatter names `cancelled`, but the payment-result screen handles paid, rejected, and `paid_stock_conflict` explicitly; any other status, including `cancelled`, falls through to the “Pago pendiente” presentation. The canonical behavior requires distinct cancelled outcomes, so this is an observed Frontend gap. The current tests do not cover cancelled result status.
- Payment initiation/confirmation tests use mocked BFF responses; the checkout test also mocks the payment-navigation helper. They do not verify a live provider, full browser round trip, stock decrement, cart cleanup, or actual PDF issuance. The navigation helper has separate URL-validation tests.
- The Frontend does not provide shipping-cost calculation or fulfillment, payment webhooks, refunds, or production payment handling. The canonical implementation record notes pending end-to-end verification for parts of the purchase lifecycle.
